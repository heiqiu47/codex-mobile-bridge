# Agent Note: Codex App 项目确认分开核验信任与原生登记

Status: implemented

## 问题

用户补充 #100 指的是 Codex App 本机项目及其 SSH 项目，而非 CLI。仅写入 `trust_level` 不能证明项目进入 App 列表；旧实现对新 SSH 目录直接要求回电脑登记。

## 决策

新建 Codex App 项目复用共享信任确认框，显示目标环境与完整路径。只读请求不写信任；确认携带绑定已登记目录、设备/inode 和 SSH 别名的摘要。每次执行重新核验目录身份，通过目标运行时的 `config/read` 获取用户层版本，以 `config/batchWrite` 只替换该规范路径的 `trust_level`，并回读确认。不会修改权限模式或批量信任其他目录。

本机仍使用原有 `codex://threads/new?path=...`，信任成功后等待 App 项目列表确认。SSH 使用安装包中核实的 `codex-app/config.json` 格式及 `codex://codex-app/apply-config` 入口，让 App 自己登记项目；不直接修改 `.codex-global-state.json`。导入前保留重试设置并检查原配置；其他主机声明、未登记项目、待改名称、不能确认当前值的全局 SSH 超时或并发修改均拒绝导入，提示在电脑 App 添加项目。

登记结果不明时保留原请求，不重复打开或创建。登记成功后保留既有 SSH 空聊天创建方式；临时 CLI 项目表与 App 的 SSH 项目表并不相同，不能要求二者存在相同项目 ID。新登记后进入线程创建阶段即记录不可自动重放状态。

SSH 列表读取同时保留 Codex App 已验证的目录归类规则：没有显式成员关系时，按同一主机下已登记项目的完整路径与聊天 cwd 精确匹配。原生项目元数据、已有成员关系、明确的无项目状态和已确认移出回执优先；本机分组规则保持原样。不按父目录、同名目录、大小写或跨主机猜测，不写入额外项目或聊天归属记录。分类写入与移出回执继续沿用 [共用会话菜单](2026-10-28-shared-session-menu.md) 的约束。

## 备选方案

只写信任配置更小，但缺少原生项目登记证据。直接改 App 全局状态能立即显示项目，却绕过原生合并、广播及同进程状态，故不采用。对全部已有远程配置重新应用更通用，但可能连接其他主机或修改全局参数，因此本轮保留明确限制，不扩大写入范围。

只检查 `thread.projectId` 或显式成员表容易回读，却遗漏 App 对旧 SSH 聊天的原生目录归类；另行导入运行时项目会制造第二套项目记录。因此采用已验证的同主机、已登记完整路径匹配，不增加原生写操作。

## 影响

用户取消信任时保留聊天名称，不创建、不发送。已有原生项目、独立聊天、CLI 和 Claude 流程保持原样。旧 App 若不支持配置导入，原生列表未确认即报告未完成，不能把配置文件写入当作成功。

本轮替代此前“Codex 留待原生确认”的范围决定，原记录保留于 [原生工作区信任](2026-10-29-remote-workspace-trust.md)。检索项目目录、原生项目创建及信任记录：Claude 的接口与账号范围仍独立保留；本篇只扩展 Codex 适配，不吸收其他客户端决策。

真实验证获用户限定授权：Mac 仓库内空测试目录及已登记的 `88server` 上空测试目录。两者均确认信任、出现在 App 原生项目列表并创建空聊天，未发送消息或运行模型。SSH 初次尝试在 `thread/start` 前被临时运行时项目映射拒绝；只读确认没有创建后，恢复旧 SSH 创建路径完成验证。定向测试覆盖只读、精确路径键、版本缺失、目录替换、确认身份变化、未知写入及其他配置保护。

本轮整体验证：后端源码 2828 项通过（81 项环境跳过），前端 1303 项通过（1 项既有跳过），浏览器既有及附件 124 项通过、补充信任确认 4 项通过；模块边界与 95 篇 Agent note 校验通过。真实验证仅覆盖当前 Mac App 与其 88server SSH 接入，不声称已在 Windows/Linux 桌面 App 验收。

SSH 归类复核纠正了此前“原生未关联”的判断：88server 的 0.160.0 运行时 `project/list` 为空，测试聊天 `projectId` 为空，Mac 显式成员表也无该聊天，但用户截图确认原生 App 已将它放在对应项目下。当前安装包 26.1023.50603 的侧边栏 `UNi` 在检查显式成员和无项目状态后，经 `MMi` 按主机与登记路径归类。这是 Bridge 漏读原生规则，不能因缺少显式 ID 再写另一套项目。DesktopIPC、线程深链和面向本地 Work 子任务的 `taskProject/assign` 均未作为 SSH 归属写入通道使用。

最小回归先复现 SSH 已登记根目录仍显示未归类，再验证目录匹配、主机隔离、显式成员优先、无项目与移出回执优先，以及项目删除后不残留归类。真实 Mac + 88server 验证中，原测试聊天和同一获准目录下新建的第二个空聊天均通过生产 `AppHosts.decorate` 返回原生项目名称和 ID；没有发送消息、执行模型或新增成员关系写入。本轮未操作 Windows/Ubuntu 网关或编译两端安装包。
