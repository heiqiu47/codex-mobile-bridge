# Agent Note: 原生工作区信任的远程二次确认

Status: implemented

## 问题

Claude Desktop Code 在未信任的目录拒绝创建会话。手机只能返回电脑确认，即使原客户端已经提供目录信任接口。Codex 的项目登记还包含桌面应用确认，单写配置不能替代。

## 决策

共享目录选择与确认界面只在原生返回 `workspace-trust-required` 且连接器报告能力时显示入口。先把目录登记为原有环境和账号范围的项目，再只读核验；二次确认显示完整目录与原生工作区信任含义，确认后调用 Claude 的 `checkTrust/saveTrust/checkTrust`。原生信任可能包含其识别的工作区，文案不声称只授权单一文件夹。

每次请求重新校验账号、环境及目录设备/inode 身份。确认只授权，不自动创建或发送；首条消息保留，用户再次点击创建。结果未知不自动重试。旧连接器继续原客户端确认，CLI、Cowork 和其他客户端不伪装支持。

用户明确选择本轮仅完成 Claude Desktop Code；Codex 保留原生确认，#100 不视为全部解决。

## 备选方案

直接写 Codex trust_level 的改动更小，但不能完成桌面项目登记，也可能改变原生审批行为，因此不采用。确认后自动重发首条消息更省点击，但混合授权与创建结果核对，因此保留明确第二次创建操作。

## 影响

新增共享目录信任路由及确认组件，原生接口封装留在 Claude 适配器。不会批量授权目录，不修改原有权限模式。旧的未支持入口继续原生确认。

验证包含 12 项项目目录后端测试、167 项 Desktop UI 测试及真实连接器代码的文件桥接夹具，覆盖取消、一次确认、重复确认只核验、账号变化、目录替换和不支持的运行环境。原生接口签名已从本机安装包核验；真实目录授权尚未执行，不能把夹具当作原客户端端到端授权证据。

检索既有信任相关笔记：SSH Claude 接入、CLI 恢复和原生归档处理不同操作，没有可合并的同一决策。
