# Agent Note: 项目引用使用附件身份并固定文件选择器滚动区域

Status: implemented

## 问题

用户实测发现，回形针多了一层大对话框，选择器只能从边缘滚动，而且顶部搜索栏随文件一起移动。项目引用追加为相对 Markdown，原生 Codex 和 Web 都没有获得与原生附件一致的交互。仅验证模型能够识别路径不足以证明附件功能完成。

## 决策

项目文件和目录保存在共享附件草稿中，正文不再拼接 Markdown。`references` 携带项目相对路径和选择时回读的宿主机绝对路径；发送端使用会话当前项目的 `Workspace.references` 再验证，不接受浏览器扩大项目边界。项目发生变化、文件消失、重复条目和符号链接不能继续发送。只读取元信息，不复制或下载内容；引用文件大小不计入上传字节限额，引用和上传仍合计最多十项。

Codex App 复用既有 `context.fileAttachments` 和附件提示包装；本地与 SSH CLI 使用同一包装。WSL 独立入口保留引用字段到队列和请求指纹中，实际派发时再次解析。Claude 和 DSH 使用网关共享的附件提示包装与历史规范化，不修改 DSH 插件及其协议。原生不支持的附件界面能力不能据此宣称已经实现。

共享 Web 渲染复用“附件：”以及下载阈值、定位、项目外短提示。回形针显示锚定按钮的小菜单；选择引用后才打开目录选择器。选择器限制整体高度，固定标题、目录操作与搜索区，列表独立滚动。iOS 新壳在这个菜单提供相册、拍照或录像、系统文件三条原生上传入口；源选择通过现有 token、主框架和同源校验，只供紧接着的系统文件选择使用。异步照片导入核对连接代次和上传票据，离开连接清理自己的临时媒体文件。旧壳和浏览器保留本机上传入口。

## 备选方案

继续采用相对 Markdown 的优点是无需扩展提交数据，但不能保留可靠的附件身份及原生点击行为，因此替换该决定。仅把链接换成绝对路径仍不能保证原生侧栏预览，也没有解决附件展示。把宿主文件先下载再上传能复用全部上传逻辑，但增加无必要的传输与副本，因此复用元信息和发送通道，而不复用内容上传。

## 影响

修改限于附件草稿、发送、历史文件索引、选择器与 iOS 文件入口，不改 DSH 插件、账号、通知或聊天主体布局。服务器升级后 Web 和 Android 可使用共享界面；iOS 三种直接上传入口需要更新原生壳。原生 Codex 侧栏点击效果仍需原生客户端实测，协议夹具成功不能代替这项验证。

定向后端回归共 153 项：152 通过、1 项按环境跳过。完整前端回归共 1305 项：1304 通过、1 项按环境跳过。Chrome/WebKit 宽窄屏定向回归 16 项通过，追加的聊天内小菜单与文件行滚动验证 4 项通过。覆盖无内容读取、目录边界、项目变化、附件重试、Codex owner/上下文、桌面历史回读、下载阈值、草稿隔离；大文件引用不占上传字节额度。模块边界和 96 篇 Agent note 校验通过。

iOS 旧 SDK 的模拟器构建通过，但它不编译 18.4+ 原生选择入口，不能作为新入口验证。Xcode 26.3 对全部主 App Swift 源码的真机目标类型检查通过。真机包依赖匹配的 iOS 26.2 运行时，用户已单独授权安装。签名、安装和真实选择器操作结果记录在本轮 `.tmp/host-attachments-20261029/`，不以类型检查代替真机验收。
