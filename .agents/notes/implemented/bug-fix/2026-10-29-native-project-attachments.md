# Agent Note: 项目引用使用附件身份并固定文件选择器滚动区域

Status: implemented

## 问题

用户实测发现，回形针多了一层大对话框，选择器只能从边缘滚动，而且顶部搜索栏随文件一起移动。项目引用追加为相对 Markdown，原生 Codex 和 Web 都没有获得与原生附件一致的交互。仅验证模型能够识别路径不足以证明附件功能完成。

## 决策

2026-10-30：下文 Claude/DSH 使用 Codex 包装和 iOS 相机入口的决定已由[原生引用与选择器恢复](2026-10-30-native-mentions-and-ios-upload-recovery.md)部分替代；保留原决定及当时证据。Codex 附件身份、项目范围和默认编辑器边界仍适用。

项目文件和目录保存在共享附件草稿中，正文不再拼接 Markdown。`references` 携带项目相对路径和选择时回读的宿主机绝对路径；发送端使用会话当前项目的 `Workspace.references` 再验证，不接受浏览器扩大项目边界。项目发生变化、文件消失、重复条目和符号链接不能继续发送。只读取元信息，不复制或下载内容；引用文件大小不计入上传字节限额，引用和上传仍合计最多十项。

Codex App 保留 `context.fileAttachments` 和附件提示包装，同时给 prepared turn 传入原生 `context.attachments`（`path`、`fsPath`、`label`），图片附带 `isImageAttachment`，追加消息同步顶层 `attachments`。`localTurnMetadata.fileAttachmentCount` 只计算非图片附件。本地与 SSH CLI 使用同一提示包装。WSL 独立入口保留引用字段到队列和请求指纹中，实际派发时再次解析。Claude 和 DSH 使用网关共享的附件提示包装与历史规范化，不修改 DSH 插件及其协议。原生不支持的附件界面能力不能据此宣称已经实现。

共享 Web 渲染复用“附件：”以及下载阈值、定位、项目外短提示。回形针显示锚定按钮的小菜单；选择引用后才打开目录选择器。选择器限制整体高度，固定标题、目录操作与搜索区，列表独立滚动。iOS 新壳在这个菜单提供相册、拍照或录像、系统文件三条原生上传入口；源选择通过现有 token、主框架和同源校验，只供紧接着的系统文件选择使用。异步照片导入核对连接代次和上传票据，离开连接清理自己的临时媒体文件。旧壳和浏览器保留本机上传入口。

## 备选方案

继续采用相对 Markdown 的优点是无需扩展提交数据，但不能保留可靠的附件身份及原生点击行为，因此替换该决定。仅把链接换成绝对路径仍不能保证原生侧栏预览，也没有解决附件展示。把宿主文件先下载再上传能复用全部上传逻辑，但增加无必要的传输与副本，因此复用元信息和发送通道，而不复用内容上传。

## 影响

修改限于附件草稿、发送、历史文件索引、选择器与 iOS 文件入口，不改 DSH 插件、账号、通知或聊天主体布局。服务器升级后 Web 和 Android 可使用共享界面；iOS 三种直接上传入口需要更新原生壳。原生 Codex 的普通 Markdown 文件点击会打开所配置的编辑器；默认侧边打开仍未实现，具体协议边界见下文。

定向后端回归共 153 项：152 通过、1 项按环境跳过。完整前端回归共 1305 项：1304 通过、1 项按环境跳过。Chrome/WebKit 宽窄屏定向回归 16 项通过，追加的聊天内小菜单与文件行滚动验证 4 项通过。覆盖无内容读取、目录边界、项目变化、附件重试、Codex owner/上下文、桌面历史回读、下载阈值、草稿隔离；大文件引用不占上传字节额度。模块边界和 96 篇 Agent note 校验通过。

iOS 旧 SDK 的模拟器构建通过，但它不编译 18.4+ 原生选择入口，不能作为新入口验证。Xcode 26.3 对全部主 App Swift 源码的真机目标类型检查通过。首次真机构建因资源编译器缺少匹配的模拟器运行时而受阻；用户授权下载后，验证了另一条构建路径：使用已有 Xcode 16.2 单独编译未修改的图标，将产物作为临时构建副本的资源，再由 Xcode 26.3 和 iOS 26.2 SDK 编译全部 Swift 源码及签名。产品源码及系统默认 Xcode 未因此改变；签名核验通过，并确认二进制包含新原生上传入口。iPhone Test 已覆盖安装并启动；不再需要本轮额外运行时下载，因此已停止该下载。

Mac Test `2.1.7-test.20261029.attachments1` 基于 `f8d2873` 编译并更新启动。372 个打包 Web 资源与提交一致，安装后的配置、会话、网络设置、正式版和原生客户端进程保护检查通过。用户单独授权了正常重启 Test 及其托管连接，未强制退出原生客户端。构建与安装证据保留在 `.tmp/host-attachments-20261029/`。新 iPhone 原生相册/拍照的真实选择操作、Codex 原生侧栏点击效果仍待用户实测，不能将签名、安装或协议验证写成这两项已通过。

## 原生消息显示修复

用户截图证明模型已读到文件，但原生消息没有附件。当前 Codex 26.1023.51421（22530）的只读协议核对发现，prepared turn 将 `context.attachments` 直接赋给原生消息的 `params.attachments`；此前 Bridge 传空数组，仅提供 composer 的 `fileAttachments`，所以模型可读不等于原生 UI 有附件。修复不改变文件内容、项目边界或历史消息。先增加文件、目录、图片及 steer 元数据断言，得到一失败两错误；补齐字段后 18 项附件测试通过。真实安装版的 native snapshot 与界面证据独立记录，不能用夹具替代。


## 最终安装版的显示与点击边界

Mac Test `2.1.7-test.20261030.recovery1` 的 LAN 消息 `FINAL_LAN_ATTACHMENT_OK_20261030_G` 与 HTTPS 消息 `FINAL_HTTPS_ATTACHMENT_OK_20261030_I` 均只发送一次，原生快照各保留一个 `测试.md` 附件；两端 Web 显示附件并收到准确回复。用户最初反馈仍不可见，但随后提供的完整 Codex 区域截图清楚显示 G 消息气泡右上方的白色 `测试.md` 标签。以截图纠正“新消息仍不可见”的判断，不能推广为旧消息字段已回填。当前原生正文解析器也能从这条真实消息恢复附件；这不是用解析成功替代截图。

用户进一步实测 I 消息的附件点击打开 VS Code。只读核验 Codex 26.1023.51421（22530）发现，`sE` 附件渲染将普通 `.md` 交给配置的文件编辑器；侧边预览条件包括支持的特定文档、视频及粘贴文本，普通 Markdown 引用不在该分支。`P2` 的打开函数支持 `openInSidePanel`，但附件字段没有传递这个选项的契约，右键菜单也继承同一判断。因此“原生附件可见”已经验证，“默认点击在 Codex 侧边打开”仍未解决。

真实考虑过以 `isPastedText` 强制走文本预览，优点是不改原生程序；但它会把文件引用误标为粘贴文本，而且历史回读重新解析普通引用时会丢失该标记，因此不采用。改变默认编辑器会影响用户其他文件操作，修改 Codex 安装包又超出授权，均不执行。保留原文件身份和原生行为，不用复制、改后缀或正文链接冒充完整修复。

证据位于 `.tmp/recovery-attachments-20261030/`：`native-final-proof.json`、`final-live.json`、`parse-native-attachment.cjs`、只读提取的附件组件及 `native-open-file.txt`。用户截图保留在该目录，临时证据不提交；原生 UI 的自动读取仍未绕过限制。
