# Agent Note: Webhook 服务预设、签名与成功判定

Status: implemented

## Problem

首版通用 Webhook 以 HTTP 2xx 判断接收成功，没有覆盖飞书的消息结构和业务返回码。用户使用默认模板测试时没有收到通知。经用户授权，以同一个临时机器人对照：通用默认结构得到 HTTP 200 / code 19002；飞书文本结构得到 HTTP 200 / code 0。只验证通用本机接收器不能证明第三方协议兼容。

## Decision

配置增加自动识别、通用 Webhook、飞书、钉钉、Discord、Telegram 协议选择。自动识别限定各官方主机和对应发送路径；显式服务选项覆盖用户自建适配入口。服务默认模板替换未修改的通用默认模板，已有自定义模板保留。默认模板由后端提供，桌面和 Web/手机共享同一份定义；前端提供显式采用所选模板的入口及占位符说明，读取状态时显示实际使用的模板。未修改的有效模板回传保存时，仍保留原默认模板标记，避免普通保存将自动模板意外变成自定义正文。

飞书发送结果以有界 JSON 响应中的业务返回码判断，不将 HTTP 200 等同于接受消息。钉钉使用 errcode，Telegram 使用严格布尔 ok；Discord 强制 wait=true，要求返回已创建消息，保留其余查询参数。错误码映射为受控提示，接收端的任意文本和异常不能直接回显。显式通用模式保留既有 HTTP 2xx 语义。飞书正文受 20 KiB 限制；Discord 文本不超过 2000 字符，Telegram 不超过 4096 字符，拒绝超限而不截断用户通知。

可选签名使用专用密钥字段：每次发送以秒级时间戳、换行与密钥组成 HMAC-SHA256 的 key，对空消息计算摘要并进行 Base64 编码，作为 JSON 顶层 timestamp/sign。该算法以[飞书官方机器人文档](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)为依据，不能套用常见的“密钥签请求体”算法。重试保留事件身份但刷新时间戳与签名。

钉钉加签是不同算法：以 secret 为 HMAC-SHA256 key，对毫秒时间戳、换行与 secret 组成的消息计算摘要，Base64 后放入经过 URL 编码的 sign 参数；timestamp/sign 每次重新生成。[钉钉官方安全说明](https://open.dingtalk.com/document/robots/customize-robot-security-settings)是其依据。不能复用飞书的空消息签名算法。

密钥只存在本地私有通知配置，GET、桌面 snapshot 和日志均不回显。空输入仅保留同一目的地的值，更换目的地或协议不自动沿用旧密钥；开启签名但缺少密钥时拒绝保存/发送。协议、签名开关与密钥摘要参与投递身份，避免旧重试沿用不同安全配置。原认证、CSRF、禁重定向、去重及通知策略不变。

用户要求像密码一样主动查看已保存的接收地址。普通配置 GET/snapshot 继续脱敏；Web 通过专用、已认证且通过 CSRF 校验的 POST 获取 URL，响应不缓存；桌面通过现有私有 read-credentials IPC 的 webhook 子项获取。此入口仅返回地址，不返回请求头或签名密钥。不预加载完整 URL，不把查看动作视为修改；迟到的读取不能覆盖新编辑，关闭后不保留已揭示地址。

## Alternatives considered

只让用户手填飞书模板可以修复消息结构，却不能解决签名与 HTTP 200 误报，不能满足本次要求。用户进一步要求常用服务的可编辑预设，故保留通用自定义模式，同时加入明确列出的服务协议。直接回显第三方响应可以提供更多诊断，但第三方可能反射凭据，改为按错误码给出受控提示。为所有供应商增加可执行签名脚本更通用，但超出范围且扩大执行面，本轮仅实现飞书、钉钉标准签名。

## Verification

已通过通知/桌面 Python 70 项、桌面/Web JS 118 项、鉴权/CSRF HTTP 3 项，以及 Chromium 390 px 手机布局 24 项、1200 px 桌面界面 22 项。验收覆盖默认格式迁移、自定义模板保护、两种签名独立计算、密钥回读/更换/清除、主动查看 URL 的访问控制、HTTP 200 业务失败、限流和未知响应、两个测试入口及既有通知回归。真实机器人结果与各平台安装记录分别保留在本地验收目录；源码测试或业务码成功不能替代用户实际收到消息的确认。用户已确认收到真实飞书文本测试消息；其他服务的协议模拟结果与真实接收确认分别报告。

## Consequences

新配置兼容现有 Webhook 数据，不改变 App 版本或手机绑定。签名校验是可选设置，与机器人端的开关应一致；关键词和 IP 白名单仍由机器人端维护。Telegram 需要在正文中填写 chat_id；Discord 默认不解析 @ 提醒。失败重试仍可能在不确定超时后重复送达。其他平台的动态签名不在本次范围内。
